Where project hashes are kept

A hash is a fingerprint of one file’s contents. When JVVV verifies a project archive, it saves the original files’ hashes in the catalogue you used. They have no expiry date. JVVV removes the reusable project hashes when you use Delete original from Q:\… and deletion succeeds. Each drive keeps its own file hashes.

Where can I find them?

Choose File → Open Catalogue Folder to locate your catalogue in File Explorer. For a verified project, the same file hash appears in two records inside that .jvvv folder.

  • The volume’s file listing lives in volumes\, in a .jvvvol file named for the volume’s unique ID. It records the hash of the file archived on that drive. Each destination has its own listing.
  • The original project record lives in catalogue.sqlite. It records the hash of each source file. Add another copy… reads the expected hashes from this record to check the new HDD.

For example, if your catalogue is on D:\ and AID-151 is E:\, both catalogue records are on D:\. The archived video is on E:\. You can unplug AID-151, close JVVV, or clear completed tasks and still reuse the project record. A catalogue snapshot taken after the archive can restore that record if you lose the catalogue.

What gets saved on the first copy?

Suppose you copy Q:\Harbour Film\Interview.mov to AID-151. JVVV calculates the video’s hash as it copies it. Then it reads the video back from AID-151 and checks that the hashes match. JVVV adds the verified project to the drive’s catalogue listing, so you can browse it immediately.

The project record keeps the source folder, the file list with sizes and modification times, each file’s hash, and which drives passed verification. It also keeps references to available previews. The video itself stays on Q:\ and the archive HDD. A hash cannot recreate a missing video.

What does JVVV read for a second drive?

If both drives start together, JVVV can read the video once from Q:\, calculate its original hash once, and write those same bytes to both drives. It reads each drive back separately so you know both copies match.

If you connect AID-152 next month, JVVV gets the video from Q:\ and the original hash from the catalogue. The first HDD can stay unplugged. JVVV checks the project’s file list, reads the video to write the new copy, then hashes the video on AID-152 and compares it with the saved hash. This saves recalculating the original hash. Reading the source is still necessary to supply the video.

What if the original project moved or changed?

Add another copy… needs the source folder at its saved path. Renaming a file, adding one, or changing its size or modification time can stop the copy at the file-list check. If a file’s contents changed but its size and time stayed the same, the read-back check catches the mismatch and the new drive stays unverified. The saved hashes still describe the version you first archived.
