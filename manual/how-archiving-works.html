How JVVV copies and verifies a project

What happens on the first copy?

Suppose you archive Q:\Harbour Film to AID-151. JVVV lists the project’s folders and files. As it reads each file to write it to AID-151, it calculates a hash, a short fingerprint of the file’s contents. With previews enabled, JVVV can use the data being copied to prepare a preview, or reuse a matching preview it already has.

After writing, JVVV reads each file from AID-151 and calculates its hash again. A match tells JVVV the file it read back has the same contents as the original. Once the project passes, JVVV records the verified files directly in AID-151’s catalogue entry. That is why the project appears immediately without scanning everything else on the HDD.

What does the catalogue keep?

  • The original project folder path, the relative paths inside it, and file details including sizes and modification times.
  • The original hash for each file and the algorithm used to calculate it.
  • Media information and preview references where available. The preview files live in the configured preview directory.
  • The volumes that received verified copies of this project.

The original media stays in the source folder and on the HDDs you copied it to. Clearing completed queue entries leaves the project record in the catalogue. A hash or preview cannot recreate the media file.

Where do the bytes for the second HDD come from?

Both HDDs connected together. When both fresh destinations are ready to write, JVVV reads a block from Q:\ and sends that block to both drives before releasing it. Each source file needs one content read and one original hash. Each destination still needs its own verification read.

Second HDD connected tomorrow. Suppose you unplugged AID-151 yesterday and now choose Add another copy… for AID-152. JVVV needs the original project at its saved path. Here is what happens to Footage\Interview.mov:

  1. JVVV checks the project listing against the saved version, including the file’s name, size and modification time. Checking these details does not require reading the video from beginning to end.
  2. JVVV opens the video on Q:\ and reads its bytes to write them to AID-152. It already has the original hash and preview record, so a fresh later copy needs no separate pass over the video to calculate another source hash.
  3. JVVV reads the video back from AID-152, hashes those bytes, and compares the result with the original hash saved yesterday.

This is what “without rescanning” means here. There is still a file-list check, a source read to supply the copy, and a destination read to verify it. No project-sized copy is kept on the PC between drives. If the source is offline, the saved record alone cannot supply the next copy.

What happens if the source changes?

On Windows, JVVV holds source files open against writes and deletions while copying and watches the folder for changes. It can keep this protection while an applied project waits for a planned drive swap. Pausing the queue or closing the app releases the protection once active work stops.

If a file has been added, removed, renamed, or visibly edited since the first archive, the saved listing can catch that before a later copy starts. If a file was edited but kept the same size and timestamp, the destination hash check can still catch the difference. JVVV reports the mismatch and leaves that destination unverified. A mismatch alone cannot distinguish an edited source from a copy error.

Resuming an interrupted archive is a different case. JVVV can recheck previously copied source files before reusing partial progress. Use Retry after resolving the reported problem.
